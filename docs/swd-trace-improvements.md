# SWD trace 改进清单（F427 实测）

> 适用对象：`trace_swd_*` 一族（SWD 两线无缝 stream）。
> 本文只写**实测支撑**的结论；未验证的一律标注「设计建议」。
> 真机环境：STM32F427VGTx + DAPLink（SWD 两线，无 SWO）+ Keil UVSOCK@4823。
> 环：`mdk_trace_swd_blob` @ `0x200020C8`，ring = `0x20002118..0x20004118`（8192 B，NSLOT=64）。

---

## 一、本轮实测的事实

### 1. 现象

- 宿主每 120 ms 搬一次环，环 8192 B，目标事件率约 **6.6 KB/s**（500 µs 粒度、1.02 B/事件）
  ⇒ 环只够 **约 1.2 s**。持续搬运时 `pending` 稳定在 ~1200 B、`lost_events = 0`，
  但**只要出现一次 `swd-stream-desync`，游标就不再推进**，环随即填满，
  `lost_events` 一路涨到 80 万+。
- 失步位置**恒定**：`ring + 7912`，即绝对地址 **`0x20004000`**（4 KB 对齐）。

### 2. 判据（三次独立实验互相印证）

| 判据 | 做法 | 结果 |
|---|---|---|
| 停机一致性 | 同一次 reset 后，halt 住读整环 | 8192 B、**tok = 8060 == 目标 `tokens` 8060**、零失步 |
| 运行态自比 | 同一区间运行态连读多遍 | 每遍都不同（`D3 85 00 00` / `86 AF 00 00` …），失步 7912 / 7915 |
| 三种切法 | 一次读 / 对半切 / 1000 步进 | 7912 处**互相都不同** |
| 图案存活 | halt 写入 ramp → run → halt 回读 | **图案完好** ⇒ 没有任何别的东西在写这块内存 |
| 环位置 | `head` 恒 = `drained + 8192`（背压钳制，不覆写），run 窗口内 `head` 未前进 | 排除「环自己被覆写」 |

### 3. 坏区形状（新增，最关键的发现）

在环内 `0x20003C00..0x20004100` 逐 64 B 写不同图案，然后 run 态连读三遍：

```
0x20003C00 … 0x20003FC0   16 个块，run#0/#1/#2 全部等于停机值   ← 忠实
0x20004000 0x20004040 0x20004080 0x200040C0
                          run#0 对，run#1/#2 错（且互不相同）  ← 坏
```

坏的表现不是「读回随机数」，而是：

- **同一个 4 字节字在整段里重复**（`n=8` 起必现；`n=4` 有时还对）；
- 该字随读的推进**单调地变**（同一次会话内 `0x078A…` → `0x07B3…`，相邻读差 ~1400）；
- **换地址也是同一个字**：`0x20004000`、`0x20004040`、`0x20004100`、`0x20004200`、
  `0x20005000`、`0x20008000`、`0x20010000`、`0x2001C000`、`0x20020000`、甚至外设
  `0x40020000` —— 全部返回同一个字。

跨总线对照（run 态）：

| 地址 | 结果 |
|---|---|
| `0x20000000`（SRAM 低） | **忠实且可重复**（读到 `"TRAP\a\0\0\0"`） |
| `0x08000000`（Flash） | 读回全 `00`（不可信） |
| `0x10000000`（CCM） | 三读不一致 |
| `0xE000ED00`（SCS） | **忠实**（`41 C2 0F 41` = 正确的 CPUID） |
| `0x40020000`（AHB1 外设） | 返回同一个「重复字」 |

### 4. 结论

> **目标全速运行时，经本机 Keil UVSOCK 链路的「读内存」不是可信通路**：
> 至少 SRAM ≥ `0x20004000` 与外设区会返回**重复的伪值**，而 SRAM < `0x20004000` 与 SCS 正常。
> 停机（halt）时同一段**逐字节吻合**，是唯一可信的搬运方式。
> 具体机制（是 Keil 侧缓存/地址译码，还是目标侧某种状态）**尚未确定**——本文件不猜。

顺带纠正一条旧结论：`linkio.need_halt_for_read()` 里写的
「批次45 复核发现 Keil 链路在目标全速运行时读得到（256 B 大块也稳）」**不成立**，
那次只覆盖了低 16 KB；≥ `0x20004000` 用同样 256 B 大块读就是伪值。
（该函数现在的返回仍是 `False`，但按批次45 的原意这正是「运行态读不可靠→先停」，
建议至少把注释与结论一起修掉。）

## 二、为什么 F401「没问题」

**F401 不是没问题。** 它撞到的是同一类故障，只是当时**用停机搬运绕过去了**，
所以没表现成「丢失」。证据在 `mdkdebug_批次56-swd无缝trace` 里记着：

> 读环必须停机：Keil 链路全速运行时读 SRAM 可能整片读回 0（已如实报 `swd-read-degenerate`）。
> 停机搬走不丢数据——靠背压保证，所以正确姿势是「跑一段 → 停机搬走 → 继续跑」。

三个要点：

1. **同一类故障、不同症状。** F401 上是「整片读回 `0x00`」（`client._degenerate_kind`
   能识别 all-zero，所以 `swd-read-degenerate` 报了出来）；F427 这轮是「整段重复同一个 4 字节字」，
   现行退化检测**认不出来**，于是被当成正常字节流去解码 → 失步 → 丢事件。
   两者是同一件事：运行态经 Keil 链路读 SRAM 读不到真值。
2. **F401 的「零丢失」是停机搬运的战果，不是运行态读可靠的证据。**
   批次56 的节拍是 120 ms「跑一段→停下来搬」，8 KB 环在 10k 事件/s 下只够 0.22 s，
   靠背压 + 停机搬运才做到 `lost_events = 0`。
3. **「F401 位置好」这个解释不成立。** F401 的 ring 是 `0x200049D0..0x200069D0`
   （blob @ `0x20004980`），**整段都落在 ≥ `0x20004000` 的区域里**；
   若坏区规则一致，F401 只会更容易踩到而不是躲开。
   所以差别只能在**搬运方式**（停机 vs 运行）与**读法**（当时 chunk = 1024、节奏 120 ms）；
   也说明坏区的地址规则是**目标/会话相关**的，不能写死成常量，
   只能靠「读法本身可信」来保证，不能靠「地址选得好」。

## 三、改进清单

分组：**A 把「不丢」变成工具能保证的语义** / **B 让「读到假数据」当场报出来** / **C 容量、命名与渲染**。
每条标注【实测支撑】或【设计建议】。

### A. 让「不丢」成为工具能保证的语义

| # | 改进 | 现状问题 | 依据 |
|---|---|---|---|
| A1 | `trace_swd_read(consistent="halt")`（**默认 halt**）：内部 `halt → 搬 → resume`，返回 `consistent`、`halt_ms`、`paused_ms` | 现在搬运路径**完全没有 halt**，纯运行态读，坏区伪值直接入流 | 【实测支撑】停机读 `tok 8060 == 目标 tokens 8060`、零失步 |
| A2 | `trace_swd_record(seconds=N, pace_ms=...)`：服务端内部循环「跑一点 → 停一下搬一点 → 继续跑」，一次调用返回完整零丢失录制 | 节拍靠调用方自己写循环；写错一次就丢一大片（本轮就是这么丢的） | 【实测支撑】批次56 F401 就是用这个姿势做到 `lost=0` |
| A3 | `trace_swd_next()`：返回 `window_ms`（环还能录多久）、`suggest_pace_ms`、`headroom_bytes`，把硬条件「节拍 < 环容量/事件率」交给工具算 | `trace_swd_status` 只报**已经丢了多少**，不报**还能录多久** | 【实测支撑】6.6 KB/s / 8192 B ⇒ 1.2 s 窗口，120 ms 节拍才安全 |
| A4 | 搬运失败/失步时的**恢复动作内建**：同一次返回里直接给出「必须 `trace_swd_reset`」+ 已丢事件数 + 增长速率，或提供 `auto_reset=true` | 现在 `swd-stream-desync` 后回滚本批且**不推进游标**（这个回滚本身是对的），但之后每次调用都卡在同一处，环立刻填满、`lost_events` 一路 80 万+ | 【实测支撑】本轮最小复现：read#1 成功，read#2/#3 全部 `swd-stream-desync`、游标卡 3175 |

### B. 让「读到假数据」当场报出来

| # | 改进 | 现状问题 | 依据 |
|---|---|---|---|
| B1 | **认出「运行态重复字」退化**：`client._degenerate_kind` 现在只认 all-zero / all-FF；应加 `repeated_word`（整段是同一个 4 字节字的重复），并在 `read_meta` 里给 `anomaly` / `repeat_word` / `run_read_untrusted` | 本轮的危险静默错答案：伪值长得像正常字节流，退化检测**完全看不见**，直接拿去解码 | 【实测支撑】`32 C6 B2 07 32 C6 B2 07` 这种整段重复，现行检测返回 `""` |
| B2 | **用目标 `tokens` 计数器自证忠实**：搬运返回 `tokens_target` / `tokens_decoded` / `tokens_delta`，不等就报错（而不是继续解码） | 宿主无从知道「我搬走的字节是不是目标写进去的那一份」 | 【实测支撑】停机读 `tok == 目标 tokens`；运行态读 `tok < 目标 tokens` 且尾部伪值 —— 这个判据一次就能定性 |
| B3 | **把「运行态读」明确标注为不可信**：`while_running=true` 且地址落在已知坏区时，`read_confidence` 直接降级并附「先 halt」的 hint；`trace_swd_status` / `read` 都应带这个标注 | 现在 `while_running` 只是个信息字段，不参与判定 | 【实测支撑】同上 |
| B4 | 把「退化/伪值 → 先停再读」这条 hint 里的**机理说准**：现在文案只讲「可能整片读回 0」，应扩展成「可能整片 0x00 / 0xFF，也可能整段重复同一个字，还可能 4 KB 以上大段不可信」 | 误导性提示会让使用者把伪值当「目标没数据」 | 【实测支撑】本轮症状（重复字、非 0）与旧文案不符 |

### C. 容量、命名与渲染

| # | 改进 | 现状问题 | 依据 |
|---|---|---|---|
| C1 | 环容量可运行期设定或至少**做一致性校验**（`trace_swd_config(cap=...)`）；host 侧读 `cap` 后与 ELF 里的 blob 尺寸交叉核对，不符就报错 | 8192 B 是编译期常量，宿主无法扩；换固件忘同步 `cap` 会静默错位 | 【设计建议】 |
| C2 | **任务泳道要能取名**：`names` 现在只映射「事件 id」（`_swd_fold` 里 `nm = names.get(i)`），0 基任务下标没有被翻成任务名的途径。应支持 `tasks=`（或读 `svcrt_task_table` 的 `entry` 符号 + ELF 反查函数名） | 现在的 trace 里**任务是无名的**，只能靠 `from/to` 下标猜 | 【实测支撑】F427 上 4 个任务泳道全部无名 |
| C3 | **IRQ 号要有通用名字映射**：实测出现 17 / 5 / 4 号 IRQ 无法命名；可从 ELF 的 `*_IRQHandler` 符号表反查（`SysTick_Handler` / `PendSV_Handler` / `EXTI…`） | 中断通道全是裸号 | 【实测支撑】 |
| C4 | 渲染页**显式声明时间粒度/单位**（`granularity` / `unit_us` / `ts_off`）：`ts_off` 时事件只有先后顺序，等距排列不能被读成等距时间 | 已有同族教训（可视化空白图比报错更危险） | 【实测支撑】三档粒度 cycle / 500us / none 都实测过 |

## 四、落地顺序建议

1. **B1 + A1**：先让「假数据」当场报出来，再把搬运默认改成停机一致 —— 这两条合起来就能把「丢事件」变成「不可能悄悄丢」。
2. **A2 + A3**：把节拍与「还能录多久」交给工具算，宿主不再自己写循环。
3. **B2**：`tokens` 自证 —— 这是最便宜、最有力的忠实度判据。
4. **C2 + C3 + C4**：渲染侧的信息量补齐（任务名、IRQ 名、时间单位）。
5. **A4 + C1**：自愈与容量。

## 五、尚不确定的部分（不写成结论）

- 坏区为什么**恰好**从 `0x20004000` 起、为什么在「首次读」时可能对一次：
  机制未定。已排除：符号重叠（ELF 无重叠）、源码显式引用（grep 无）、哈希不一致
  （固件与主机 `slot_of` 逐项相同）、环被覆写（`head` 钳制不覆写）、
  `read_mem_verified` 复读（改单次读后照旧）、工程声明内存范围（uvprojx IRAM = `0x20000000` + `0x30000`，覆盖全片）。
- 「坏区是绝对地址属性还是与目标/会话相关」：本轮只测了 F427 一台、F401 板未接。
  因此**不要**把 `0x20004000` 硬编码成常量，正确做法是让读法本身可信（A1）或可自证（B2）。

## 六、落地进度（F427 真机复验）

清单一出就分批落地，这里只记**已经能在真机上跑出来**的部分；没做的照实留着。

| # | 状态 | 落地形态 / 证据 |
|---|---|---|
| A1 | **已完成** | `trace_swd_read(consistent=...)` 默认 **halt**（停下→就地重读控制块→搬→推游标→恢复），返回 `consistent` / `halt_ms`；`run` / `auto` 作为显式选项保留。真机 20 轮连续录制：**0 失败**。⚠️ 这里原先还写了「录制期间 `lost_events` 不再增长」，那是**没有逐轮记录就下的结论，作废**——第六节的复验数据只记了成功调用数，第七节逐轮记录后看到的是：能不能不丢取决于「粒度 × 节拍 × 环容量」，与 halt 本身无关 |
| B1 | **已完成** | `_swd_fake_kind()` 认三类伪值：`all_zero` / `all_ff` / **`repeated_word`**（滑动窗口找「同一 4 字节字连续重复 ≥12 窗」，不假设对齐；同时排除「字节全同的 HITN 密集段」这种正常流）。检出即报 `swd-read-untrusted` / 退化标记，**不拿去解码** |
| B2 | **部分** | 返回体里给了目标侧 `tokens` / `events` / `lost_events` / `lost_bytes`（`ctrl` 段），可以把「搬到的」与「目标记的」对照；**但还没做成自动比对失败即报错**（`tokens_target` vs `tokens_decoded` 的硬判据未落） |
| B3 | **部分** | `read_meta` 里有 `while_running` / `read_confidence` / `degenerate`，退化时附「先 halt」的 warning；尚未按地址段做置信度降级（坏区规则还没定论，见第五节） |
| B4 | **已完成** | 退化/伪值的报错与提示文案改成三类并列（整片 0x00 / 0xFF / 整段重复同一个字），不再只说「可能读回 0」 |
| C2 | **已完成** | ① `tasks=auto` 在会话内解析一次 `svcrt_task_table[i].entry`（偏移来自 DWARF）→ 反查 ELF 函数名 → 历史事件回头重补；② **支持多份镜像** `elf="内核.axf;app.axf"`，任何一份里的入口都能配上名字；③ **跨镜像的名字必须过内容核对**（板上机器码 == .axf 同地址字节），核不过/核不了就丢名并记 `unconfirmed_slots` —— 地址对上不等于板上跑的是这份构建。F427 实测：4 个槽位拿到名字，3 个跨镜像槽位如实留空 |
| C3 | **部分** | 中断轨道不再被任务名污染（0xF 既是 idle 任务号也是异常号，两者是两个命名空间），Cortex-M 异常按符号名/异常号给名；**外设 IRQ 号仍是裸号**（未做 `*_IRQHandler` 反查） |
| C4 | **已完成** | 时间线页面显式声明时间口径与单位（`granularity` / `unit_us` / `ts_off`），`ts_off` 时明说「横轴是事件序号，间距不代表时间」；`view_render` 出的单文件 HTML 带这些 limit 说明 |
| A5 | **已完成** | `trace_swd_read(only_new=...)`：默认 `events` 给**会话尾部**（含前几次调用的事件、互相重叠），`only_new=true` 才只给**本批新增**。自己拼线性轨迹时搞错就会把同一段时间数很多遍（第一版网页就是这么错的，见 7.5） |
| A2 / A3 / A4 / C1 | **未做** | 服务端内部录制循环、`trace_swd_next` 的「还能录多久」预算、失步自愈、环容量运行期校验 —— 都还停在建议 |

## 七、时间粒度：一个「看得见的错答案」和它的代价（F427 真机实测）

### 7.1 现象
用户看着第一版网页说：**「任务切换怎么这么慢而且只有一次」**。页面上时长 44 s、
上下文切换 12081 次，看着像模像样；泳道里却只有 1~2 段。

### 7.2 机理（在设备侧，不在渲染侧）
`kernelsrc/components/mdk_trace/mdk_trace_swd.c::mdk_trace_swd_event()`：

```c
now = SWD_NOW(); dt = now - s_last_cycles; s_last_cycles = now;
... else if (c->dt_unit != 0u) { dt = dt / c->dt_unit; }   /* 整数除法，余数丢掉 */
```

余数**丢弃且不累加**。粒度比事件间隔粗时，每条都算出 0；`dt == 0` 走 HITN 分支，
只写 1 字节、**不写 dt**，宿主读回来就是 0。宿主把 dt 当「与上一条的时间差」累加，
时间轴便**冻在原点**。

本轮实测（F427，事件率约 5000~6700 条/s，平均间隔 ~150~200 µs）：

- 粒度 `500us`（`dt_unit=48000`）：逐批检查 **`dt==0` 占 100%**，`t_us` 全是 0.0。
- 粒度 `1us`（`dt_unit=96`）/ `cycle`（`dt_unit=0`）：`dt!=0` 占 **100%**，时间轴正常。
- 粒度 `10us`（`dt_unit=960`）：`dt!=0` 约占 **30%** —— 也就是「同一 10 µs 桶里的
  事件（中断进/出成对）dt=0，跨桶的那条带上时间」。**时间轴仍然是对的**，因为
  绝对时刻是逐条累加出来的，不是靠每条都有增量。

> 判据：**只要有相当比例的事件带增量、且累加出来的时间跨度与挂钟对得上，轴就是真的。**
> 「dt==0」本身不等于冻结；「**本批全都**是 0」才是。宿主侧据此报 `time_axis_frozen`。

### 7.3 代价：粒度换的是字节预算

环 8192 B（编译期常量）、停机搬运一轮 ~0.9~1.4 s（halt 本身 ~0.45~0.55 s），
所以可持续搬运能力约 **6~9 KB/s**。粒度定的就是「每条事件多少字节」：

| 粒度 | unit_us | B/事件 | dt!=0 | 一轮（0.05 s 节拍）丢多少 |
|---|---|---|---|---|
| cycle | 0.0104 | 3.33 | 满 | lost 每轮 +490 |
| 1us | 1.0 | 2.33 | 满 | lost 每轮 +260 |
| 2.5us | 2.5 | 2.32 | 满 | 跟不住 |
| **10us** | 10.0 | **1.31** | ~30% | **+162（≈2.7%）** |
| 50us | 50 | 1.32 | 部分 | +1790 |
| 500us | 500 | 1.01 | 少 | 时间轴冻结 |

**结论**：细粒度才能有真时间轴，但每事件字节数上去；一旦生产速率超过搬运能力，
就进入**正反馈**——丢一条 ⇒ 目标清字典 ⇒ 下一条必是 LIT（5+ 字节）⇒ 更快填满 ⇒
丢更多（实测 `lost` 增量 664→721→1538→2345→3163→5207，一路加速）。
10 µs 是这台机器上的实测甜点：1.31 B/事件 ≈ 5.6 KB/s，刚好跟得上。

**真解**仍是 C1（8192 B 的环太小，应可配/可校验）与 A2/A3（把节拍交给工具算），
不是继续在宿主侧抠。

### 7.4 顺带发现的两处宿主侧坑

**(a) `events` 是会话尾部，不是本批新增。** 第一版采集脚本写的是
`events.extend(out["events"])`，于是存下来的是 N 个互相重叠的窗口：78454 条里
大量是同一段时间被数了很多遍，看着条数很壮观。要拼一条能离线回放的线性轨迹，
必须取尾部 `new_events` 条 —— 现在给了显式开关 `only_new=true`。

**(b) `limit` 给太大反而更容易丢。** `limit` 是「返回会话最后多少条」，给成 20 万时
每轮都要把**整个会话**序列化成 JSON 喂回来，单次调用越来越慢，环就在调用期间溢出：
实测前 10 轮不丢、第 11 轮起丢且加速（`lost` 增量 2299 → 33570）。把 `limit` 压到
刚好盖住本批（7000）后，同样 24 轮从「lost +33570」降到「**lost +2299**」。
→ 连 7.3 的正反馈一起看：**慢一点点的搬运循环，代价是指数级的丢**。

### 本轮顺带修掉的一处「错数字」

渲染适配层把「事件」badge 写成 `len(evs) * thinned`：没抽稀时 `thinned = 0`，
于是**满屏轨道配一个「事件 0」**；抽稀时又是估算值（8 条报成 10 条）。
同一处 `limits` 文案还写着「统计口径仍是全量」，而 sched/fault 计数其实是在**抽稀后**
的子集上数的。现已把「统计口径」与「绘图口径」分开：总数在抽稀前记下，
类型计数一律走全量事件，文案改成「每 N 条抽 1 条**绘制**（总数与下面的计数仍是全量）」。
（属于「空白图 / 零计数比报错更危险」那一类，见 `docs/PITFALLS.md`。）
